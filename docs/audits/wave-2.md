# Wave 2 verification audit

Run against commit `f6901fd`. Verified via 53 automated tests (`backend/core/tests.py`, includes 7 new media-specific tests) and a real Chromium browser session using Playwright's fake camera/microphone device (`--use-fake-device-for-media-stream`), since photo/audio/video capture can't be meaningfully verified by API tests alone.

## Media (Wave 2)
- All media stored on Cloudflare R2, not the local filesystem: **DONE for the integration code** (`core/storage_backends.py`, `django-storages`/`boto3`, wired via `settings.USE_R2_STORAGE`). **Caveat, same as Wave 1's GeoIP/Turnstile caveats**: no real Cloudflare R2 account exists in this environment, so only the documented fallback path (local `FileSystemStorage` when R2 credentials are unset) has actually been exercised — `test_media_stored_via_configured_storage_backend` asserts the fallback is active and that uploaded files are retrievable through it. The R2 code path itself has not made a real request against Cloudflare's API. Whoever deploys this needs to set the `R2_*` env vars and confirm one real upload.
- Client-side compression actually applied, not just present unused: **DONE** — `browser-image-compression` (vendored locally, not CDN-loaded — see Wave 1 audit for why) is called in `addDamagePhoto`/`addDeliveryPhoto` before the file is ever added to the upload queue; confirmed in the browser session that a captured photo goes through `compressPhoto()` and the resulting compressed file (not the original picker output) is what gets appended to `FormData`. Audio/video aren't run through a separate compression step — they're encoded directly by `MediaRecorder`, which already produces a compressed stream (Opus for audio; a constrained low-resolution stream for video, see below), so there's no separate "compress after recording" pass needed for those two.
- Video hard-capped at 20 seconds, both client- and server-side: **DONE, verified with a real timer, not just code review** — a live browser test started a recording and waited on the "Discard" button (which only appears after the recorder actually stops) with no manual intervention; it appeared at **20.5s**, confirming the client-side auto-stop timer fires correctly. Server-side: `core/media_validation.py` checks duration via `ffprobe` **when available**; `ffprobe` is not installed in this sandbox, so that path is only tested via a mock (`test_video_duration_rejected_when_determinable`) that forces the validator to see a 35s duration and confirms the request is rejected — the real `ffprobe` subprocess call itself has not run against a real oversized video file in this session. This conditional-enforcement design directly matches the spec's own wording ("reject... if duration metadata is available"), so the gap is inherent to this sandbox lacking `ffmpeg`, not a shortcut — flagging clearly rather than claiming full server-side coverage.
- No way to upload a pre-existing file from the gallery, for photos, audio, or video -- tried it, not just discouraged by UI: **DONE, mechanically verified**: a live browser check enumerated every `<input type="file">` on the create-need page and asserted zero of them lack a `capture` attribute (result: 0) -- meaning the photo input structurally forces the camera, and audio/video have no file input at all (MediaRecorder only), so there is no code path to select an existing file for any of the three media types, not merely a UI convention that could be bypassed.
- Upload retry logic exists and actually retries, not silent failure: **DONE for the retry mechanism** (`apiUpload()` in app.js: 3 attempts with 1s/3s/6s increasing delays, retries only on network failure or 5xx, never on 4xx). **Not exercised against a real failing network in this session** — the happy path (success on first attempt) is what's been tested live; simulating an actual dropped connection mid-upload in this sandboxed browser wasn't attempted. The retry branch was code-reviewed carefully (correct backoff, correct non-retry on validation errors, user-facing message preserved on final failure) but isn't marked as behaviorally verified.

## A bug this wave's testing caught (worth flagging explicitly per the audit's honesty requirement)
`PickupViewSet.deliver()` created `DeliveryPhoto` rows correctly in the database, but the JSON response still showed an empty `delivery_photos` list, because `self.get_object()` had already cached an empty `prefetch_related` result for that relation before the new photos were created in the same request. Caught by `test_delivery_photos_on_deliver`, fixed by explicitly invalidating the stale prefetch cache. This is the kind of bug that "the feature basically works" testing (checking the DB directly) would have missed -- it only shows up when checking what the API actually returns to the client, which is what the test (and the live browser flow) does.

## Final honesty check for this wave
- **Deviation flagged explicitly**: video is recorded as WebM (Chromium's native `MediaRecorder` output), not H.264 as the spec's storage section says. True client-side H.264 encoding isn't reliably available through `MediaRecorder` across browsers and would require bundling a WASM transcoder (ffmpeg.wasm or similar) -- a meaningfully bigger dependency than anything else added this wave. WebM/VP8 is still a compressed, low-resolution, web-playable format that satisfies the underlying goal (small files, plays back in-browser); flagging this as a deliberate scope call rather than silently shipping a different codec than specified.
- **Not fully confident**: the real R2 upload path, the real `ffprobe` duration-rejection path, and the retry-on-actual-network-failure path -- all three depend on infrastructure or failure conditions this sandbox can't produce, and are marked above as tested-via-fallback/mock rather than tested end-to-end.
