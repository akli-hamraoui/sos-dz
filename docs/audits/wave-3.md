## Security and reliability (Wave 3)
- Moderation uses NSFWJS (self-hosted, free), no paid third-party API or billing key: **DONE, and unusually well-verified for this project's constraints** -- the NSFWJS classification model ships bundled inside the `nsfwjs` npm package, so a genuinely real moderation service (`moderation-sidecar/`, real Express + TensorFlow.js) runs fully offline in this sandbox. This is not mocked or stubbed: `test_real_sidecar_classifies_a_benign_photo` posts a real image over real HTTP to the real running sidecar and asserts on its real response, and a live browser session did the same through the actual UI (captured a photo, watched the live model classify it, confirmed it rendered). This is the one Wave 3 dependency this sandbox could fully exercise, unlike GeoIP/Turnstile/R2.
- Every uploaded photo/video goes through moderation before being publicly visible (when the toggle is on): **DONE** -- `DamagePhoto` and `DeliveryPhoto` each carry their own `moderation_status` now (a gap from Wave 2, closed this wave: previously only `Need` had one, meaning individual photos couldn't be independently hidden); serializers omit the `image` URL entirely (return `null`, not a broken link) unless `moderation_status == approved`. Confirmed via `test_high_score_auto_rejects_and_hides_image_url` / `test_intermediate_score_goes_to_pending_queue_and_hides_image_url` that the URL is genuinely absent, not just marked, at both the "rejected" and "pending" ends.
- Three-tier outcome (auto-approve / auto-reject / pending human review), not simplified to two: **DONE** -- `core/moderation.py:status_for_score()`, thresholds configurable via `NSFWJS_APPROVE_THRESHOLD`/`NSFWJS_REJECT_THRESHOLD`. All three branches have a dedicated test with a mocked score.
- "Report this content" button present and works independent of the moderation toggle: **DONE** -- `test_report_content_hides_it_immediately_independent_of_toggle` explicitly sets `media_moderation_active = False` first and confirms reporting still hides the content; the frontend button is unconditionally rendered next to every approved (visible) media item.
- Duplicate detection suggestion appears at creation time for similar needs in the same wilaya within 24h: **DONE** -- `find_similar_needs()` (difflib text similarity, spec explicitly allows "doesn't need to be sophisticated"), exposed both as a standalone pre-submit check and attached to the create response. **Additional real-world confirmation beyond the test suite**: while browser-testing an unrelated feature, a leftover need from an earlier test session in the dev DB matched a newly-created one with a similar title, and the app correctly surfaced the "similar need exists, view it instead?" prompt and honored the choice (Playwright's default dialog auto-dismiss took the "view existing" branch, and the app correctly redirected instead of creating a duplicate) -- an unplanned but real end-to-end confirmation.
- Duplicate and content reports both reach an admin-reviewable queue: **DONE** -- `DuplicateReportAdmin`/`ContentReportAdmin`, both filterable by status, both with dedicated admin actions (merge/dismiss, restore/confirm-rejection) that are logged in `AuditLog` (`test_admin_moderation_action_is_logged`, and the merge action's own test asserts the reported need actually gets cancelled).
- GPS coordinates outside the Algeria bounding box are rejected server-side with a graceful fallback, not a hard error: **DONE** (built ahead of schedule in Wave 1, since the "update GPS after creation" flow needed it then) -- re-confirmed this wave with `GPSBoundingBoxTests`, and note this is a 400 with a clear message the frontend can display, never a 500.
- The NSFWJS service is documented in DEPLOYMENT.md and runs as its own managed systemd service that survives a reboot: **DONE** -- full unit file, install steps, and health-check command added to `DEPLOYMENT.md`. Like the rest of `DEPLOYMENT.md`, the systemd unit itself has not been applied against a real server (no VPS access in this environment) -- the commands are written to be copy-paste-exact, not run-and-confirmed on real hardware.

## Deliberate simplifications / known gaps, stated plainly
- **`ffmpeg` is not installed in this sandbox.** Two things depend on it: the Wave 2 video-duration cap (server-side half only -- client-side cap is fully verified, see Wave 2 audit) and this wave's video-frame extraction for moderation. Both are coded to degrade safely when `ffmpeg` is absent (duration check skipped; video moderation queues to "pending" rather than auto-approving), and this is now explicit in `DEPLOYMENT.md`'s NSFWJS section as something to install on the real VPS. Neither path has been exercised against a real oversized/inappropriate video in this session -- only via mocks.
- **`npm audit` on `moderation-sidecar/` reports 4 vulnerabilities (3 high, 1 critical)**, all in `@tensorflow/tfjs-node`'s transitive install-time tooling (`@mapbox/node-pre-gyp` -> `tar`/`adm-zip`), not in the running server's request path. `npm audit fix --force` would downgrade to an unusably ancient tfjs-node -- not a real fix. Documented as a known, accepted, currently-unresolved upstream situation rather than silently ignored.
- Duplicate similarity uses `difflib.SequenceMatcher` on concatenated title+description text with a fixed 0.5 threshold -- deliberately simple per spec's own allowance, not tuned against real-world data (no real dataset available to tune against).
- The "report as duplicate" frontend flow asks the reporter to type the other need's ID via a plain `prompt()` rather than a proper search/picker UI -- functional but rough; a nicer picker is a reasonable follow-up but wasn't worth the time this wave given the spec's "speed over polish" priority and that Wave 5 is where visual design gets a real pass.
