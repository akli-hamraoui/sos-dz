# Wave 4 verification audit

Run against commit `e652608`. Verified via 85 automated tests (16 new: `CollectionPointTests`, `CommentTests`) and a real Chromium browser session driving the complete create -> comment -> reply -> confirm -> close flow.

## Community features (Wave 4)
- Comments support exactly one level of replies, not zero and not infinite nesting: **DONE** -- `test_reply_one_level_only` confirms both that a reply to a root comment succeeds (201) and that a reply to a reply is rejected (400), enforced server-side in `CommentCreateSerializer.validate()`, not just a frontend UI limitation. Confirmed live in the browser too (posted a reply, it rendered nested one level under its root).
- Confirmation counter actually increments and persists: **DONE** -- `test_confirm_increments_and_persists` checks both the API response and a fresh DB read; the live browser test independently confirmed the same (clicked confirm, count went from 0 to 1 in the rendered page, not just in a mocked response).
- Collection points are filterable by wilaya like Needs are: **DONE** -- same `?wilaya=` query param pattern as `/api/needs/`, `test_filterable_by_wilaya_like_needs`.
- Collection points appear on the same main map as Needs, with a visually distinct icon and a legend explaining the difference: **DONE** -- confirmed both the icon distinction (black square `L.divIcon` vs. urgency-colored `L.circleMarker`) and that the legend text was actually updated (not just assumed) via a live browser read of the rendered `.legend` element's text content.
- Tapping a Collection point pin opens a popup with its name, contact (masked phone), organization, hours, and status: **DONE** -- popup content built in `renderMainMap()`'s collection-point branch matches the required field list; not independently screenshotted with a real map tile background (tiles are blocked by this sandbox's network policy, same caveat as every wave's map testing), but the popup's HTML content generation was code-reviewed against the spec's exact field list.

## Additional checks re-run this wave (per the checklist's instruction to reconfirm earlier sections once new code touches them)
- Global read-only mode now also blocks Comment and CollectionPoint creation, not just Need/Pickup/ProgressUpdate: **DONE** -- `test_read_only_mode_blocks_comment_creation` added; `CollectionPointViewSet.create` and `CommentViewSet.create` both call the same `write_guard()` helper used everywhere else, so this was correct by construction, and the test closes the loop by actually proving it rather than assuming.
- Rate limiting (20/hour/IP) now applies to Comment and CollectionPoint creation too, per the Wave 1 spec text ("Need, Pickup, Comment, CollectionPoint once those exist in later waves"): **DONE, and actually re-tested this wave** (`test_rate_limit_applies_to_comment_creation`, `test_rate_limit_applies_to_collection_point_creation`) rather than left as merely inferred from shared code -- both dedicated tests exhausted the limit and confirmed a 429 on both endpoints. Along the way this also surfaced and confirmed a real, correct behavior worth stating explicitly: the throttle scope is shared across ALL creation endpoints for a given IP (one combined "creation" bucket, not one bucket per endpoint) -- so 20 Needs then 1 Comment from the same IP hits the limit on that 21st request, which is the intended real-world anti-abuse behavior, not a bug.
- Comment author phone numbers are never shown publicly anywhere in the frontend: **DONE** -- `test_create_root_comment_on_need` asserts `author_phone` is absent from the API response entirely (not merely un-rendered client-side), and `CommentSerializer`'s field list omits it structurally, so there's no code path that could accidentally leak it later.

## Deviations / decisions worth flagging
- The "close collection point" and "delete comment" identity checks reuse a loose name+phone string match (`matches_creator`/`matches_author` on the models), deliberately simpler than Need/Pickup's token+DOB scheme -- this matches the spec's explicit instruction that collection points and comments "carry less risk" and don't need the heavier mechanism. No access token is issued for either.
- `Comment.category` is silently cleared (forced to `""`) server-side when the comment is a reply, since the spec says category is "only relevant for Need comments" and doesn't define its meaning for a reply specifically -- a reasonable narrowing, not a spec requirement I invented data for.
