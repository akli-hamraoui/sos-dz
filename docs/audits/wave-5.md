# Wave 5 verification audit

Run against commit `721ab34`. Wave 5 has no backend changes (87 backend tests still passing, unaffected), so this audit is entirely about the new React/Vite frontend, verified through a production build + preview server and several live Chromium browser sessions (dev-mode for functional flows, a real `npm run build` + `vite preview` for the PWA/offline-cache claims specifically, since a dev server doesn't run a real service worker).

## Finishing (Wave 5)
- The app is installable as a PWA: **DONE, verified against the production build** -- `manifest.webmanifest` fetched and parsed live (`name: "Rassemble"`, `display: "standalone"`, 2 icons), and `navigator.serviceWorker.ready` resolved with an active worker after loading the built app once. **Not tested on an actual phone** (no physical device in this sandboxed environment) -- the checklist explicitly asks for a real-phone test, which is the one item here I cannot do myself; the manifest/service-worker/installability preconditions are all confirmed correct, but the literal "install icon shows on a phone's home screen" step wasn't observed firsthand.
- Offline creation of a Need/Pickup/ProgressUpdate actually queues locally and syncs automatically on reconnect -- tested by actually going offline, not just reading the code: **DONE**. A live browser session set the Playwright browser context fully offline (`setOffline(true)`, not a mocked flag), submitted a Need, confirmed via a direct IndexedDB read that exactly 1 record was queued (not silently dropped), confirmed the app showed the "pending sync" message and navigated on rather than hanging, then set the context back online and confirmed via a second direct IndexedDB read that the queue drained to 0 -- meaning the queued record was actually POSTed to the real Django backend and accepted, not just marked as synced client-side.
- Arabic mode actually flips the layout to RTL across every screen, not just the text direction of paragraphs -- checked navigation, cards, buttons, forms: **DONE**. Screenshotted four screens in Arabic after a live language switch: home, the create-need form (the most field-dense screen -- selects, radios, fieldsets, a floating action button), the needs list (card list + list/map toggle), and collection points. All four mirror correctly: bottom nav icon order reverses, the list/map toggle's rounded corners swap sides, form labels and fields align to the right, fieldset legends and radio groups flow right-to-left. This is a direct result of `src/index.css` using CSS logical properties (`margin-inline-*`, `border-inline-*`, `inset-inline-*`, `border-start/end-radius`) throughout rather than physical `left`/`right` properties.
- User-generated content is never auto-translated: **DONE by construction** -- only strings passed through `t()` come from the translation files; Need titles/descriptions, comments, contact names etc. are rendered verbatim from API responses, never routed through i18next.
- Language choice persists across app restarts: **DONE** -- `localStorage` key `rassemble_language`, read on `i18n.js` module load before the first render.

## Deviations / known rough edges, stated plainly
- **Leaflet popups render raw HTML strings** (`marker.bindPopup(...)`), not React components, because Leaflet's popup content lives outside React's virtual DOM. The "Open" links inside map popups are therefore plain `<a href="/needs/:id">` tags that trigger a full page reload instead of a client-side route transition. Functionally correct (verified: clicking them does navigate to the right page), just not as smooth as an SPA transition. Fixing this properly would mean rendering popups via React portals -- judged not worth the complexity for this wave.
- **Server-side error messages in forms are shown as raw JSON** (e.g. `{"detail":"..."}`) rather than formatted/translated text -- this was already true of the Wave 1-4 Alpine app (same pattern) and wasn't improved in the migration; a real polish item, not a regression.
- **A real bug was found and fixed during this wave's own testing, not before shipping it**: `api.js`'s `createOrQueue()` was double-prefixing API paths (`"/api" + "/api/needs/"`), which 404'd every single online Need creation. This is exactly the kind of thing the checklist's "actually test it, don't assume" instruction is meant to catch -- it would have been invisible from reading the code or from the backend's own test suite (the bug was entirely in how the frontend constructed the URL), and only surfaced once a live browser actually tried to submit the form.
- **PWA cross-origin caveat documented, not resolved**: once the frontend and backend deploy to different domains (frontend via IONOS Deploy Now, backend via the IONOS VPS), the service worker's offline GET cache is scoped to the frontend's own origin. `DEPLOYMENT.md` now flags this explicitly and recommends a same-origin reverse-proxy setup for `/api`/`/media` rather than leaving it undocumented for whoever deploys this next.
